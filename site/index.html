Chapter 0 — Start here: the 10-minute quick win

The one-sentence version: keep the model warm, shrink the context window to what you actually use, drop to the smallest model that still answers well, and time it so you can see the difference.

  1. Keep the model loaded (2 min). Ollama unloads after 5 minutes of quiet — that's the "first message takes forever" feeling. OLLAMA_KEEP_ALIVE=1h ollama serve
  2. Shrink the context (3 min). Reserved context costs speed even when unused. Everyday Q&A: "options": {"num_ctx": 2048} (or 4096 for longer documents).
  3. Try the smaller model (3 min). ollama run llama3.2:3b — if it answers your daily questions well, that's your new daily driver: roughly 2–3× faster than an 8B.
  4. Time it (2 min). bash scripts/bench-ollama.sh llama3.2:3b — write the numbers down, change one thing, run it again. That's the whole secret of this book.

Chapter 1 — Why is it slow? (Diagnose before you tune)

Types fast but pauses mid-answerMemory pressure / CPU-GPU thrash5, 6

The three numbers to know: time to first token (what "feels instant" is made of), tokens per second (how fast the words flow), and total time. Every tuning chapter targets these, and the stopwatch in chapter 7 is the referee.

Chapter 2 — Turbo settings (the ones that actually matter)

OLLAMA_KEEP_ALIVE — warm engine
Stay-loaded timer. Default 5m of quiet, then unload (=> slow first message back). Set 1h for a whole working session.
num_ctx — context window (the quiet speed killer)
Every reserved token costs memory and compute even if unused. 2048 for Q&A, 4096–8192 for document work. Per model with /set parameter num_ctx 2048.
OLLAMA_FLASH_ATTENTION — free speed, with a caveat
Faster attention implementation. Try it; if the stopwatch doesn't improve, drop it without guilt.
OLLAMA_KV_CACHE_TYPE=q8_0 — half the scratchpad, none the wiser
Keeps the KV cache at 8-bit: ~87% of the memory, essentially no quality cost. Use q4_0 (~48%) when every byte counts.

Make them permanent with a systemd override (sudo systemctl edit ollama) — the full snippet is in docs/02-turbo-settings.md.

Chapter 3 — Cache reuse: never pay the same tax twice

  • Cache 1 — the model itself. Pin it with one API call: {"keep_alive": "1h"}. Check who's loaded with ollama ps.
  • Cache 2 — repeated beginnings. Same system prompt + same document first, question last → Ollama reuses the work. Reword or reorder the shared part and you break the cache (and pay again).
  • Cache 3 — downloads. Both-daily drivers pinned means neither ever pays load tax. Warm-up ritual after reboot: one throwaway question. 20 seconds, done.

Chapter 4 — Smaller-model shortcuts: the ladder

RungSizeSame-machine feelRight job
10.5–1BInstantQuick facts, rewrites, classification
23BSnappyEveryday Q&A, summaries, emails
37–8BComfortableLong drafting, trickier reasoning
413B+SlowSpecialist work, dedicated hardware

The pairing habit: keep a quick model (1B/3B) for 90% of messages and a deep model (7–8B) for the rest. Start quick; re-ask deep only when the answer feels thin. Don't shrink past usefulness: repeated sentence shapes and forgetfulness mean go up a rung.

Chapter 5 — CPU vs GPU pinning (laptops, Pis, and where the work happens)

Run ollama ps and read the PROCESSOR column:

  • 100% GPU — best case. You're done; enjoy.
  • CPU — fine for small models, slow for big ones. On laptops with efficiency/performance cores, pin with taskset -c 4-7 ollama run ....
  • 70%/30% CPU/GPU — the often-missed speed bug. Splits feel far slower than the numbers suggest. Fix by dropping num_gpu (fewer layers on a nearly-full GPU beats a constant spill), smaller quant, or smaller num_ctx.

Raspberry Pi: all-CPU world; small quantized 1B–3B models are genuinely pleasant there. Apple Silicon Macs: unified memory means no pinning at all — chapter 4 is your whole sport.

Chapter 6 — Quantization in plain English

Quantization = storing the model with fewer decimal places. Smaller file, less RAM, faster loads; each extra compression costs a little quality. Decode the codes: q4_K_M = 4-bit K-quant, medium rounding care — the everyday sweet spot.

Quant~Size (8B)Quality feelWho it's for
q4_K_M~4.7 GBGood — fine for everydayLaptops, Pis, GPUs
q5_K_M~5.7 GBSlightly sharperWhen RAM allows
q8_0~8.5 GBHard to distinguish from fullMemory-rich machines
q2/q3~2–3.5 GBGets confidently wrongOnly when nothing else fits

Two rules: below q4 quality drops fast; above q5 gains get tiny. And a smaller model at a higher quant often beats a bigger model at a lower quant in the same memory.

Chapter 7 — The hotel-AI speed test (stopwatches and scorecards)

Feelings are terrible measuring tools. This test borrows what a hotel front desk cares about — run by hand with any stopwatch, or run the script:

bash scripts/hotel-speed-test.sh llama3.2:3b --out scorecard.txt
EventWhat it measuresWhat verifies it
1. Cold check-inFully cold interaction: server + load + answerkeep-alive fixes (ch. 3)
2. Warm wake-up"You phoned ahead" — model already loadedwarm-start bonus (ch. 3)
3. Follow-up"And one more thing…" — cached conversationprompt cache intact (ch. 3)
4. Big luggageA few pages of text + one questionnum_ctx / KV cache (ch. 2, 6)

The rules: one change between scorecards · same prompts and machine state · write it down · no improvement is a result, not a failure. A scorecard you can't compare is a story, not a test.

Chapter 8 — The month-refresh ritual (15 minutes)

  1. Update Ollama. curl -fsSL https://ollama.com/install.sh | sh
  2. Look at the shelf. ollama list — prune never-touched models; check for newer/smaller tags of favorites.
  3. Re-run the hotel test. Watch for regressions, not records.
  4. Health panel. bash scripts/perf-set-check.sh · ollama ps · df -h / · free -h
  5. Prune settings drift. Are the Big Four the values that measured well, or just felt interesting?
  6. Log one line. The scorecards are the log.

Set a calendar reminder titled "AI pit stop." Short ritual, honest stopwatches, small keeps.
